# Contract: 결과 생성 API

**Feature**: `001-job-recommendation-keywords` | **작성일**: 2026-10-11
**스키마 정의**: 필드 규칙은 `data-model.md`가 기준이다. 이 문서는 요청·응답·오류의 형식과 화면 상태 대응만 다룬다.

## 1. 엔드포인트

| 항목 | 값 |
|------|----|
| 경로 | `POST /api/generate` (Vercel 서버리스 함수 `api/generate.ts`, 서버에서만 실행) |
| 요청 | `Content-Type: application/json`, 본문 32KB 이하, 본문 = `GenerateRequest` (data-model 1.2) |
| 성공 응답 | `200`, 본문 = `{ "ok": true, "result": ResultPayload }` (data-model 2.2) |
| 실패 응답 | 3절의 상태 코드, 본문 = `{ "ok": false, "error": ApiError }` |
| 인증 | 없음(Phase 1). Phase 2에서 로그인 세션을 요구하도록 바꾼다 |
| 캐시 | 사용하지 않음. 응답 헤더 `Cache-Control: no-store` |
| 클라이언트 제한 | 요청은 한 번에 하나, 120초에 `AbortController`로 중단 |
| 서버 제한 | 시도당 55초, 재요청 포함 합계 110초, `maxDuration = 120` |

그 밖의 경로와 메서드는 `405`를 반환한다. 같은 프로젝트에서 AI 제공자를 직접 호출하는 클라이언트 코드는 없다(원칙 IX).

## 2. 요청 처리 순서

```
1. 본문 크기 확인 (32KB 초과 → VALIDATION_FAILED)
2. 요청 제한 확인 (초과 → RATE_LIMITED)            ← 비싼 작업 전에
3. Zod 검증 (엄격 객체: age 등 모르는 필드 → VALIDATION_FAILED)
4. 입력 보호 검사 (식별 정보 → PII_DETECTED)
5. ModelInput 구성 (번호 부여)
6. 프롬프트 구성 → LLM 호출 (시도당 55초)
7. 응답 파싱 + Zod 검증 + 의미 검증 V1~V13
8. 실패 → 같은 입력으로 1회 재요청(규칙 번호만 전달) → 다시 7
9. 그래도 실패 → OUTPUT_INVALID
10. 성공 → 표시용 값(label, value, notice) 추가 후 반환
```

로그에는 `requestId`, 단계 이름, 결과 코드, 소요 시간, 재요청 여부, 오류 코드만 남긴다. **요청·응답 본문, 입력 값, 모델 응답 원문, 프롬프트는 남기지 않는다.** SDK 오류 객체를 그대로 출력하지 않고 상태 코드와 오류 이름만 기록한다(원칙 VI, spec FR-040).

## 3. 오류 코드와 화면 상태

| 오류 코드 | HTTP | 발생 조건 | 화면 상태 (design 14절) | 안내 문구 | 행동 | 입력 유지 |
|-----------|------|-----------|--------------------------|-----------|------|-----------|
| `VALIDATION_FAILED` | 400 | Zod 검증 실패, 한도 초과, 모르는 필드, 본문 과대 | **입력 화면 필드 오류 + 오류 요약** (design 12절) | 항목별 문구(`details`의 필드 경로 → `messages.ts`) | 오류 항목으로 이동 | 유지 |
| `PII_DETECTED` | 400 | 식별 정보 형식 감지 | **입력 화면 필드 오류** (해당 입력창) | "이름·연락처 같은 개인 식별 정보는 입력하지 않아요. 해당 부분을 지워 주세요." | 해당 입력창 포커스 | 유지 |
| `RATE_LIMITED` | 429 | 요청 제한 초과: 같은 사용 환경에서 10분 20회 초과(초기값, FR-038, 환경 변수로 조정). `Retry-After` 헤더 포함 | **요청 제한** (노랑 배지) | "짧은 시간에 요청이 너무 많았어요. 잠시 기다린 뒤 다시 시도해 주세요. 입력하신 내용은 그대로 남아 있습니다." | 다시 시도, 입력 수정하기 | 유지 |
| `UPSTREAM_FAILED` | 502 | LLM 호출 실패, 연결 오류, 공급자 5xx, 공급자의 속도 제한 | **생성 실패** (빨강 배지, FR-023) | "연결이 원활하지 않았어요. 입력하신 내용은 그대로 남아 있습니다. 다시 시도해 주세요." | 다시 시도, 입력 수정하기 | 유지 |
| `OUTPUT_INVALID` | 502 | 재요청 후에도 스키마·의미 검증 실패 | **형식 오류** (생성 실패 배지, 부분 결과 없음, FR-020) | "결과 형식이 맞지 않아 보여드릴 수 없어요. 입력하신 내용은 그대로 남아 있습니다. 다시 시도해 주세요." | 다시 시도, 입력 수정하기 | 유지 |
| `TIMEOUT` | 504 | 서버 합계 110초 초과 | **시간 초과** (빨강 배지, 클라이언트 120초 화면과 동일 상태, FR-023) | "시간이 너무 오래 걸려 멈췄어요. 입력하신 내용은 그대로 남아 있습니다. 다시 시도해 주세요." (구체 시간을 쓰지 않아 서버 110초와 화면 120초 중 어느 쪽이 먼저여도 문구가 맞다) | 다시 시도, 입력 수정하기 | 유지 |
| `INTERNAL` | 500 | 예상하지 못한 오류, 설정 누락(API 키 없음) | **생성 실패** | 위와 같음 (원인은 화면에 노출하지 않음) | 다시 시도, 입력 수정하기 | 유지 |
| (클라이언트) 120초 중단 | - | 서버 응답 전에 클라이언트 타이머 만료 (요청을 보낸 시점부터 센다, 재시도 시 0초부터) | **시간 초과** | `TIMEOUT`과 같음 | 다시 시도, 입력 수정하기 | 유지 |
| (클라이언트) 화면 이탈 | - | 분석 중에 뒤로 가기·다른 화면 이동 | 입력 화면(결과 없음) | 없음 | - | 유지 |
| (클라이언트) 네트워크 오류 | - | `fetch` 자체 실패 | **생성 실패** | 생성 실패와 같음 | 다시 시도, 입력 수정하기 | 유지 |
| (클라이언트) 응답 형식 오류 | - | 응답이 약속된 `{ok}` 형식이 아님 | **생성 실패** | 생성 실패와 같음 | 다시 시도, 입력 수정하기 | 유지 |

- **실패 유형별 안내**(원칙 X): 연결·내부 오류는 "생성 실패", 결과 형식 오류는 "형식 오류", 지연·중단은 "시간 초과", 요청 제한은 "요청 제한"으로 문구를 구분한다.
- 서버가 재요청을 하는 동안에도 클라이언트 타이머는 계속 간다. 서버가 120초 전에 `TIMEOUT`을 반환하면 즉시 시간 초과 화면으로 간다.
- **생성 실패와 요청 제한은 다른 화면이다**(FR-038). 공급자의 속도 제한(429)은 우리 쪽 요청 제한과 원인이 다르므로 `UPSTREAM_FAILED`로 처리한다.
- 서버 오류의 원인(공급자 이름, 상태 코드, 스택)은 응답 본문에 넣지 않는다.
- `VALIDATION_FAILED`가 서버에서 돌아오는 경우는 클라이언트 검증을 우회했거나 두 쪽 규칙이 달라졌다는 뜻이므로 오류 요약에 항목을 보여주고, 서버 로그에는 규칙 번호만 남긴다.
- "분석 중"과 "지연(30초)"은 오류가 아니라 진행 상태이며 응답 코드와 무관하게 클라이언트 타이머로 만든다(FR-023).

## 4. `ApiError` 형식

```json
{
  "code": "RATE_LIMITED",
  "message": "짧은 시간에 요청이 너무 많았어요. …",
  "retryAfterSeconds": 60,
  "details": [
    { "path": ["strengths", 1], "rule": "required" }
  ],
  "requestId": "r_9f2c…"
}
```

| 필드 | 설명 |
|------|------|
| `code` | 3절의 코드 중 하나. 화면 상태는 이 값으로만 정한다 |
| `message` | 위 표의 안내 문구. 클라이언트가 그대로 쓸 수 있지만 문구의 기준은 `messages.ts`이다 |
| `retryAfterSeconds` | `RATE_LIMITED`일 때만. **화면에는 숫자를 표시하지 않는다**(spec FR-038). 재시도 버튼은 바로 누를 수 있고, 다시 제한되면 같은 화면이 나온다 |
| `details` | `VALIDATION_FAILED`, `PII_DETECTED`일 때만. `path`는 입력 필드 경로, `rule`은 규칙 이름. **입력 값은 넣지 않는다** |
| `requestId` | 문의·로그 대조용. 입력과 관련 없는 무작위 값 |

## 5. 요청·응답 예시 (형태만, 값은 가상)

요청(나이 없음):
```json
{
  "education": { "level": "bachelor", "status": "graduated" },
  "majors": ["사회복지학"],
  "noCareer": false,
  "careers": [{ "jobTitle": "생활지도 교사", "industry": "지역아동센터", "period": "2년" }],
  "intern": { "has": false },
  "certifications": ["사회복지사 2급"],
  "trainings": [],
  "strengths": ["상대의 이야기를 끝까지 듣는다", "맡은 일은 계획을 세워 끝까지 마무리한다", "처음 보는 사람과도 대화를 편하게 이끈다"]
}
```

성공 응답은 `{ "ok": true, "result": { "jobs": [3개], "keywords": [3개], "notice": [2줄], "generatedAt": "…" } }` 형태이며 각 항목은 data-model 2절의 필드를 갖는다.

## 6. 계약 테스트 (Vitest, LLM 모의)

| 테스트 | 기대 결과 | 관련 |
|--------|-----------|------|
| 요청에 `age`가 있음 | 400 `VALIDATION_FAILED`, LLM 호출 0회 | FR-004 |
| 강점 2개 / 4개 | 400, `details.path = ["strengths"]` | FR-008 |
| 강점에 주민번호 형식 | 400 `PII_DETECTED` | FR-009, 원칙 VI |
| 모의 LLM이 직업 2개 반환 | 재요청 1회 후 `OUTPUT_INVALID`, 부분 결과 없음 | FR-020, 원칙 VIII |
| 모의 LLM이 첫 응답 실패, 두 번째 성공 | 200, LLM 호출 정확히 2회 | 원칙 VIII |
| 모의 LLM이 존재하지 않는 항목 번호 지목 | 거부(V3), 재요청 | FR-013 |
| 모의 LLM 출력에 `%` 또는 `연봉` | 거부(V8) | FR-017 |
| 모의 LLM이 성공해도 `notice` | 항상 두 줄 포함(모델 출력과 무관) | FR-016 |
| 제한 초과(21번째 요청) | 429 `RATE_LIMITED`, `Retry-After`, LLM 호출 0회 | FR-038 |
| 로그 캡처 | 어떤 입력 값도 로그 출력에 없음 | 원칙 VI |
| API 키 | 클라이언트 번들과 응답에 키 문자열 없음 | 원칙 IX |
