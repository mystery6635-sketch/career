# Research: 기술 선택 이유와 대안

**Feature**: `001-job-recommendation-keywords` | **작성일**: 2026-10-11
**전제**: 기술 스택은 사용자가 지정했다(React + Vite + TypeScript, Tailwind, Zod, 서버리스 함수에서만 LLM 호출, Vercel 무료, DB 없음, Vitest + Playwright). 이 문서는 각 선택의 이유와 검토한 대안, 그리고 스택만으로는 정해지지 않아 이 계획에서 결정한 사항을 기록한다.
**표기**: 외부 서비스의 가격·한도·버전처럼 이 문서 작성 시점에 확인하지 못한 값은 "확인 필요"로 둔다.

---

## 0. 먼저 해결할 충돌: "DB 없음"과 명세의 로그인·저장

| 항목 | 내용 |
|------|------|
| 충돌 | 요청한 스택은 "DB 사용 안 함, 저장 안 함"이다. 그러나 spec은 US6(로그인, P1), US7(이력 저장, P2), US8(구직자 기록, P3)과 FR-030~035를 범위 안으로 둔다. Constitution v2.0.0도 이 저장을 전제로 개정되었다. |
| 결정 | 이 계획의 **구현 범위는 US1~US5(생성·검증·복사·인쇄·재시도·재생성)와 FR-001~029(저장 관련 제외)** 이다. US6~US8, FR-030~035는 **다음 단계(Phase 2)** 로 미룬다. |
| 근거 | 1인 개발 MVP에서 가치의 핵심은 US1이다(spec US1 Why). 저장 없는 구조가 개인정보 위험이 가장 작다(원칙 VI). 미룬 기능은 spec에서 삭제하지 않으므로 원칙 XI(범위 준수)를 어기지 않는다. |
| 이 단계의 "저장" 버튼 | 화면에는 두되 **비활성**으로 표시하고 "상담 이력 저장은 아직 준비 중이에요"를 글자로 안내한다. 눌러도 아무것도 저장하지 않는다. (design 13.6) |
| Phase 2 후보(참고, 확정 아님) | 인증 + 저장소를 한 곳에서 무료로 제공하는 서비스(예: Supabase 무료 플랜, Firebase 무료 플랜)가 후보다. 한도와 가격은 확인 필요. Phase 2 시작 전에 별도 research로 확정한다. |
| 위험 | 로그인이 없는 동안 생성 API가 공개된다. 비용 폭주 위험은 4절(요청 제한)과 6절(운영 보호)로 줄인다. 이 위험은 사용자가 확인해야 한다. |

> **사용자 확인 필요**: Phase 2를 이 계획 안에 포함할지, 위 결정대로 나눌지. 포함하려면 "DB 없음" 요구를 바꿔야 한다.

## 1. 프레임워크: React + Vite + TypeScript (Vercel 서버리스 함수)

- **Decision**: Vite 최신 안정 버전, React, TypeScript strict. 서버 코드는 `api/generate.ts`(Vercel 서버리스 함수)와 `server/`에 둔다.
- **Rationale**: 화면(React)과 서버리스 함수(LLM 호출, 비밀 키 보관)를 한 저장소에서 처리해 1인 개발자가 관리할 것이 적다(원칙 IX, XV). Vercel이 Vite 정적 빌드와 `api/` 함수를 함께 배포한다(함수 진입 형식과 실행 시간 한도는 확인 필요). 서버리스 함수에서만 LLM을 호출하므로 API 키가 브라우저에 노출되지 않는다.
- **Alternatives**:
  - Vite + 별도 Express 서버: 배포 대상이 둘로 늘어 1인 개발에 부담.
  - Remix / SvelteKit: 사용자가 지정한 스택이 아니고 얻는 이점이 이 규모에서는 작다.

## 2. 스타일: Tailwind CSS + CSS 변수 토큰

- **Decision**: Tailwind CSS v4의 CSS 우선 설정(`@theme`)에 design.md 16~19절 토큰을 선언한다. 선언한 값은 CSS 변수로도 노출된다. 토큰 이름은 시안 CSS 변수(`--navy-950`, `--teal-700`, `--mint`, `--err` 등)를 그대로 쓴다.
- **Rationale**: 시안이 CSS 변수 기반이라 이름을 유지하면 시안과 코드를 1:1로 대조할 수 있다. 토큰을 한 곳에만 정의하면 대비·색 수정이 한 번에 된다.
- **Alternatives**: CSS Modules(토큰 재사용 규칙을 직접 만들어야 함), styled-components(런타임 비용, Server Component와 궁합이 나쁨), Tailwind v3 설정 파일(v4가 CSS 변수와 더 직접 연결됨. 단 버전은 구현 시 확인).
- **간격·글자 크기 토큰**: 시안에 변수가 없고 값으로 쓰였다(design 확인 필요 17번). **결정**: 색은 시안 이름 그대로, 글자 크기·간격은 Tailwind 기본 척도에 가장 가까운 값이 아니라 **시안 값을 그대로 임의 값 토큰으로 선언**한다(예: `--text-body: 17px`). 4px/8px 척도로 정리하는 일은 하지 않는다. 이유는 시안과 달라질 위험을 피하기 위해서이다.

## 3. 입력·출력 검증: Zod

- **Decision**: Zod 스키마를 `shared/schema/`에 한 번만 정의하고, 클라이언트 폼 검증, 서버 요청 재검증, LLM 응답 검증에서 같은 모듈을 가져다 쓴다.
- **Rationale**: 한도(FR-037)와 구조(직업 3개, 키워드 3개)를 한 곳에서 바꾼다. TypeScript 타입이 스키마에서 나오므로 화면과 서버의 필드 불일치가 컴파일에서 잡힌다(원칙 VII, VIII).
- **Alternatives**: Valibot(번들이 작지만 지정 스택이 아님), Yup(타입 추론이 약함), 직접 작성(오류 문구와 한도가 흩어짐).
- **한계와 보완**: Zod만으로는 "근거 항목이 실제 입력에 존재하는가", "수치가 섞였는가" 같은 의미 검증을 못한다. 이를 위해 `validate-output`(의미 검증 함수)를 Zod 뒤에 둔다(data-model 5절).
- **오류 문구**: 시안에 확정된 문구(design 12절)를 Zod 메시지로 그대로 쓴다. 문구 사본이 여러 곳에 생기지 않도록 `shared/messages.ts` 한 파일에서 관리한다.

## 4. 요청 횟수 제한 (FR-038)

- **문제**: Vercel 서버리스는 요청마다 다른 인스턴스가 처리할 수 있어서, 메모리에만 저장한 횟수는 인스턴스 사이에서 공유되지 않는다. 정확한 제한에는 외부 저장소(예: Redis)가 필요하지만 "DB 없음"과 맞지 않는다.
- **Decision**: **최선 노력(best-effort) 메모리 제한 + 공급자 쪽 월 사용 한도**의 두 겹으로 한다.
  1. 서버 메모리의 슬라이딩 윈도우. 키는 IP를 해시한 값이며 원본 IP는 저장·로그하지 않는다. 초기값은 **IP당 10분에 20회** (확인 필요: 한 기관이 같은 IP를 쓰면 상담사 여럿이 한도를 나눠 쓴다. 시범 운영 후 조정).
  2. LLM 공급자 콘솔의 월 사용 한도(소프트·하드). 이것이 **비용 폭주를 실제로 막는 최종 방어선**이다.
- **Rationale**: 메모리 제한은 한 인스턴스 안의 단순 반복 호출(버튼 연타, 단순 스크립트)을 막는다. 여러 인스턴스에 분산된 공격은 막지 못하지만, 최종 비용은 공급자 한도가 막는다. 새 서비스를 추가하지 않아 원칙 XV에 맞다.
- **Alternatives**:
  - Upstash Redis 무료 플랜: 정확하지만 외부 서비스가 하나 늘고 "DB 없음" 요구와 어긋난다. 입력 내용이 아니라 횟수 카운터만 저장하므로 개인정보 위험은 없다. 운영에서 메모리 제한이 부족하다고 확인되면 도입한다(한도·가격 확인 필요).
  - Vercel 방화벽/속도 제한 기능: 플랜별 제공 여부와 한도 확인 필요.
  - 제한 없음: 비용 폭주 위험이 커서 불가(요청 사항).
- **동작**: 초과하면 HTTP 429와 오류 코드 `RATE_LIMITED`, `retryAfterSeconds`를 반환하고 화면은 "요청 제한" 상태를 보인다(contracts 3절).

## 5. LLM 공급자와 호출 방식

- **Decision**: 공급자는 한 파일(`server/ai/client.ts`)에만 두고 환경 변수 `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`로 바꿀 수 있게 한다. 기본값은 Anthropic Messages API이며 모델은 저비용 모델(`claude-haiku-5-5`)로 시작한다. 품질이 부족하면 `claude-sonnet-5-5`로 올린다.
- **Rationale**: 사용자가 공급자를 지정하지 않았다. 한국어 품질, JSON 출력 안정성, 지침 준수(프롬프트 주입 방어)를 기준으로 삼았다. 호출 코드를 한 곳에 모으면 공급자를 바꿔도 나머지 코드가 달라지지 않는다. **가격과 한도는 확인 필요**이다. 무료 LLM API는 한도와 개인정보 처리 조건이 불확실해 기본값으로 쓰지 않는다.
- **Alternatives**: OpenAI, Google Gemini(모두 가능하며 `client.ts`만 교체). 무료 한도 모델(조건 확인 필요, 구직자 이력이 학습에 쓰이는지 약관 확인이 먼저).
- **개인정보**: 구직자 이력이 외부 LLM 서버로 전송된다. 이름·연락처·나이는 보내지 않는다(FR-004, FR-029, 원칙 VI). 공급자의 데이터 보관·학습 정책은 **확인 필요**이며, 운영 전에 기관 개인정보 처리방침과 맞는지 상담사 소속 기관이 확인해야 한다.
- **출력 형식 강제**: 시스템 프롬프트로 "JSON만"을 요구하고, 응답을 Zod로 검증한다. 공급자의 구조화 출력(스키마 강제) 기능은 쓸 수 있으면 켜되, 이 기능이 없어도 동작하도록 서버 검증을 기준으로 삼는다(원칙 VIII).
- **재요청**: 1회. 첫 응답이 스키마 또는 의미 검증에 실패하면, 실패 이유(필드 경로와 규칙 이름만, 입력 내용 제외)를 짧게 알려 한 번 더 호출한다. 그래도 실패하면 `OUTPUT_INVALID`를 반환한다. 부분 결과는 표시하지 않는다(FR-020).

## 6. 시간 제한과 Vercel 실행 시간

- **요구**: 클라이언트는 30초에 지연 문구, 120초에 중단(FR-023).
- **Decision**: 라우트에 `maxDuration = 120`을 선언한다. 시도 1회당 서버 제한은 **55초**, 재요청까지 합쳐 **110초**를 넘기지 않는다(110초 후 `TIMEOUT` 반환). 클라이언트는 `AbortController`로 120초에 요청을 끊고 "시간 초과" 화면을 보인다.
- **확인 필요**: Vercel 무료(Hobby) 플랜의 함수 최대 실행 시간. 120초가 허용되지 않으면 시도당 제한을 줄이고 재요청을 생략하는 순서로 줄이되, 줄이는 경우 spec FR-023의 120초 문구와 어긋나므로 spec 수정 여부를 사용자가 결정한다. 구현 시작 전에 Vercel 문서로 확인한다.
- **Alternatives**: 스트리밍 응답(첫 글자가 빨리 보이지만 "부분 결과 금지"와 충돌), 백그라운드 작업 + 폴링(구조가 복잡하고 저장소가 필요).

## 7. 상태 유지: 클라이언트 메모리 (React Context)

- **Decision**: 입력과 결과는 루트 레이아웃의 Context에만 둔다. `localStorage`, `sessionStorage`, 쿠키, URL에는 두지 않는다. 입력 → 결과 이동은 클라이언트 라우팅이라 상태가 유지된다. 새로고침하면 사라지고, 결과 화면은 "빈 화면" 상태가 된다(design 14절).
- **Rationale**: spec Assumptions("저장하지 않은 입력과 결과는 화면을 닫으면 사라진다")와 원칙 VI를 가장 단순하게 지킨다. 구직자 정보가 브라우저 저장소에 남아 공용 PC에 잔존하는 위험이 없다.
- **Alternatives**: `sessionStorage`(새로고침에 강하지만 탭에 개인정보가 남는다. 공용 상담 PC에서 위험. 사용자가 "클라이언트 상태로만"이라고 했으므로 메모리 상태만으로 충분), URL 쿼리(주소·기록·서버 로그에 입력이 남는다, 불가).
- **트레이드오프**: 실수로 새로고침하면 입력을 잃는다. 이 위험은 하단 고정 바 안내와 결과 화면에서의 "입력 수정하기" 경로로 줄이지만 완전히 없애지 못한다. 필요하면 spec 변경으로 `beforeunload` 경고를 추가한다(지금은 추가하지 않음, 원칙 XI).

## 8. 화면 이동과 시안 차이

- 시안의 해시 경로(`#/main`)는 실제 경로로 바꾼다: `/`(메인), `/input`(입력), `/result`(결과 + 상태 화면 전부). 분석 중, 빈 화면, 실패, 시간 초과, 요청 제한은 `/result`가 상태에 따라 보여주는 화면이다.
- 시안의 **인쇄 미리보기 화면**은 프로토타입 확인용이므로 별도 화면으로 만들지 않는다. 인쇄는 `window.print()`와 `@media print` 스타일로 구현한다(요청 사항, design 15절).
- 시안 맨 위 "시안 도구" 띠는 구현하지 않는다(design 3절).
- 화면 전환 시 포커스를 H1로 옮기고 `document.title`을 갱신하는 동작은 react-router 경로 변경 후 클라이언트 훅으로 구현한다(design 22절).

## 9. 접근성·인쇄·반응형 검증 도구

- **Decision**: 단위 테스트는 Vitest, E2E는 Playwright(Chromium)에서 뷰포트 1440×900, 1024×768, 390×844와 `page.emulateMedia({ media: 'print' })`를 쓴다. 접근성 자동 점검에는 `@axe-core/playwright`를 추가한다(새 의존성, 필요성: WCAG 대비·이름·역할 점검을 직접 만들 수 없음. 자동 점검은 일부만 잡으므로 design 26절의 수동 확인을 대체하지 않는다).
- **A4 한 장 확인**: Chromium의 `page.pdf({ format: 'A4' })` 결과의 페이지 수가 1인지 본다. 이 방식은 실제 프린터 출력과 다를 수 있어 최종 확인은 수동이다.
- **Alternatives**: Cypress(지정 스택이 아님), Storybook(1인 개발에 유지 부담, 공통 컴포넌트는 E2E와 단위 테스트로 충분).
- **LLM 없이 테스트**: E2E는 `page.route`로 `/api/generate`를 가짜 응답으로 대체한다. 서버 통합 테스트는 `LLM_PROVIDER=mock`(개발·테스트 환경에서만 허용, 프로덕션 빌드에서는 거부)을 쓴다. 실제 LLM을 쓰는 페르소나 점검은 사람이 `npm run eval:personas`로 따로 실행한다(비용 때문에 CI에 넣지 않는다).

## 10. 글꼴

- **Decision**: `@fontsource`로 IBM Plex Sans KR과 IBM Plex Mono를 빌드 시 내려받아 자체 호스팅한다. 대체 글꼴은 Noto Sans KR → sans-serif.
- **Rationale**: 실행 중 외부 글꼴 서버 호출이 없어 속도와 개인정보(방문자 정보 외부 전송)에 유리하다. design 확인 필요 18번(대체 글꼴)의 답이 된다.
- **확인 필요**: 글꼴 라이선스 조건(두 글꼴 모두 오픈 폰트 라이선스로 알고 있으나 배포 전 최종 확인), 한글 글꼴 용량(한글은 용량이 커서 사용 굵기를 400/500/600/700으로 제한한 값이 번들 크기에 주는 영향은 측정 필요).

## 11. 결과 문구의 톤과 금지 표현 (design 24절 → 프롬프트·검증)

design 확인 필요 23번의 답이다. 톤 규칙을 **세 곳**에서 같은 근거로 적용한다.
1. **시스템 프롬프트**: 금지 표현과 대체 표현을 그대로 넣는다(`prompts/system-prompt.md`).
2. **출력 의미 검증**: 금지 표현 목록과 수치 패턴을 코드로 검사해, 걸리면 재요청 대상으로 처리한다(data-model 5절).
3. **페르소나 점검**: 사람이 읽고 "구직자와 함께 봐도 괜찮다"를 확인한다(원칙 XII 검토 기준). 자동 검사는 쉬운 말인지 판단하지 못한다.

금지 표현 검사는 완전하지 않다(모든 부정 표현을 사전으로 막을 수 없다). 그래서 프롬프트와 사람 검토를 함께 쓴다.

## 12. 표준 직업명(FR-036)

- **문제**: "한국고용직업분류 직업명인가"를 서버가 확인하려면 분류 목록 데이터가 필요하다. 이 계획에는 그 데이터가 없다.
- **Decision**: LLM이 `isStandardName`을 스스로 표시하고, `false`이면 화면에 "표준 분류 확인 필요" 배지를 붙인다. 서버는 이 값을 검증하지 못한다.
- **위험**: LLM이 표준 이름이라고 잘못 표시할 수 있다. 그래서 프롬프트에 "확실하지 않으면 false"를 명시해 표시가 과하게 빠지지 않게 한다. 그래도 남는 위험은 상담사가 직업명을 확인한다는 안내문(FR-016)에 맡긴다.
- **개선 후보**: 고용24 등 공공 분류표를 정적 목록으로 포함해 서버에서 대조한다. 데이터의 이용 조건과 최신성은 **확인 필요**이며 이 계획에는 넣지 않는다.
