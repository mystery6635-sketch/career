# 구직자 초기상담 지원 앱 Constitution

## 프로젝트 개요

직업상담사가 구직자 초기대면상담 중 학력, 전공, 경력, 나이, 인턴 경험, 자격증, 교육이수 내용,
구직자 본인이 생각하는 강점 3개를 입력하면, AI가 (1) 취업 가능성이 높은 추천 직업 3개와 추천 근거,
(2) 자기소개서에서 강점과 직무를 연결할 수 있는 키워드 3개와 간단한 설명을 생성하는 웹 앱이다.
주 사용자는 직업상담사이며 결과는 상담 중 구직자와 함께 확인한다. 1인 개발이며 무료·저비용
도구로 MVP를 구축한다.

## Core Principles

### I. 상담사 중심 보조 (AI as Assistant)
**규칙**: AI는 상담사의 판단을 보조한다. 최종 판단과 안내는 상담사가 한다. 결과 화면에는 항상
"참고용 결과이며 상담사와 함께 검토가 필요하다"는 안내를 표시해야 한다(MUST).
**이유**: 직업 선택은 구직자의 삶에 영향을 주는 결정이며, AI 결과를 확정 판단으로 오해하면 안 된다.
**검토 기준**:
- 결과 화면에 위 안내 문구가 항상 표시되는가? (예/아니오)
- 인쇄·복사된 결과물에도 해당 안내가 포함되는가? (예/아니오)
- 결과를 "확정", "반드시" 등 단정적 표현으로 제시하는 문구가 없는가? (예/아니오)

### II. 입력 연결 근거 필수 (Evidence-Linked Output)
**규칙**: 모든 추천 직업과 키워드는 사용자가 입력한 항목(학력, 전공, 경력 등)과의 연결 근거를 함께
제시해야 한다(MUST). 근거 없는 추천은 출력하지 않는다.
**이유**: 상담사와 구직자가 추천 이유를 확인·반박할 수 있어야 신뢰와 검토가 가능하다.
**검토 기준**:
- 추천 직업 3개 각각에 입력 항목을 명시한 근거가 있는가? (예/아니오)
- 키워드 3개 각각에 입력 항목을 명시한 근거가 있는가? (예/아니오)
- 근거가 비어 있는 항목이 화면에 출력되지 않도록 검증하는 테스트가 있는가? (예/아니오)

### III. 강점 존중과 객관 정보 보강 (Strength Grounding)
**규칙**: 구직자가 입력한 강점 3개는 존중하되 학력·경력·자격증·교육이수 등 객관 정보와 연결해
근거를 보강한다. 객관 정보와 연결되지 않는 강점은 그 사실을 부드럽게 안내한다.
**이유**: 자기 인식은 중요한 출발점이지만 자기소개서에서는 뒷받침 사례가 설득력을 만든다.
**검토 기준**:
- 강점 3개 각각이 결과에서 다뤄지는가? (예/아니오)
- 객관 정보와 연결된 강점에 연결 항목이 표시되는가? (예/아니오)
- 연결되지 않는 강점에 비하하지 않는 안내 문구(보완 방향 포함)가 표시되는가? (예/아니오)

### IV. 검증되지 않은 수치 금지 (No Unverified Figures)
**규칙**: AI는 검증되지 않은 수치(취업률, 연봉, 채용 공고 수 등)를 생성하지 않는다. 확인이 필요한
정보는 "확인 필요"로 명시한다. "취업 가능성이 높은" 표현을 쓰려면 추천이 입력된 이력과의 적합도에
기반하며 채용 수요나 취업을 보장하지 않는다는 안내를 화면, 복사물, 인쇄물에 함께 표시해야 한다.
**이유**: 근거 없는 수치는 구직자의 의사결정을 왜곡하고 상담사의 신뢰를 해칠 수 있다.
**검토 기준**:
- 프롬프트에 수치 생성 금지와 "확인 필요" 표기 지침이 포함되어 있는가? (예/아니오)
- 출력에서 출처 없는 수치를 탐지·차단하는 검증이 있는가? (예/아니오)
- 샘플 입력 테스트 결과에 출처 없는 취업률·연봉·공고 수가 없는가? (예/아니오)
- "취업 가능성" 표현이 있는 화면·복사물·인쇄물에 적합도 기준과 비보장 안내가 함께 있는가? (예/아니오)

### V. 차별 방지 (Non-Discrimination)
**규칙**: 나이, 학력, 경력 공백, 인턴 경험 부재 등을 이유로 특정 직업을 배제하거나 부정적으로
평가하는 표현을 사용하지 않는다. 고용상 차별로 이어질 수 있는 추천 논리를 금지한다.
**이유**: 결과가 차별적 판단의 근거로 쓰이면 구직자에게 직접적인 피해를 준다.
**검토 기준**:
- 프롬프트에 차별적 배제·부정 평가 금지 지침이 명시되어 있는가? (예/아니오)
- 나이가 높거나 경력 공백·인턴 경험 없음 입력에서도 부정적·배제적 표현이 없는가? (예/아니오)
- 위 케이스를 포함한 차별 방지 테스트가 자동 또는 수동 체크리스트로 존재하는가? (예/아니오)

### VI. 개인정보 최소 수집과 통제된 저장 (Privacy by Minimization and Controlled Storage)
**규칙**: 개인정보는 최소한으로 수집한다. 주민번호 등 고유식별정보는 받지 않는다. 구직자 기록에는
이름과 선택적 연락처만 저장할 수 있으며, 이 식별 정보는 추천 결과 생성 입력에 포함하지 않는다.
저장은 로그인한 상담사가 명시적으로 실행할 때만 하고, 저장 데이터는 소유한 상담사 본인만 접근할 수
있다. 저장된 이력과 기록은 마지막 갱신 후 1년이 지나면 자동 삭제하며 상담사가 언제든 삭제할 수
있다. 저장을 실행하지 않은 입력과 결과, 입력 본문의 로그는 서버에 남기지 않는다.
**이유**: 취업 관련 정보는 민감하다. 저장이 필요해진 만큼 수집 범위, 접근 통제, 보관 기간을 제한해야
유출 위험과 법적 부담을 줄일 수 있다.
**검토 기준**:
- 입력 폼과 구직자 기록에 주민번호 등 고유식별정보 필드가 없는가? (예/아니오)
- 저장 동작을 상담사가 명시적으로 실행하기 전에는 입력·결과가 서버에 저장되지 않는가? (예/아니오)
- 이름·연락처가 추천 생성 요청에 포함되지 않는가? (예/아니오)
- 다른 상담사 계정과 로그인하지 않은 사용자는 저장 데이터에 접근할 수 없는가? (예/아니오)
- 1년 후 자동 삭제와 상담사 직접 삭제가 동작하는가? (예/아니오)
- 서버 로그에 입력 본문이 남지 않는가? (예/아니오)
- 식별 정보로 보이는 입력(주민번호 형식 등)을 감지해 경고하거나 차단하는가? (예/아니오)

### VII. 입력 검증 (Input Validation)
**규칙**: 필수 항목 누락, 비정상 값, 과도한 길이의 텍스트, 프롬프트 주입 시도를 처리해야 한다(MUST).
**이유**: 잘못된 입력과 악의적 입력은 부정확하거나 위험한 AI 출력으로 이어진다.
**검토 기준**:
- 필수 항목 누락 시 항목별 오류 안내가 표시되는가? (예/아니오)
- 항목별 최대 길이와 허용 값 범위가 정의되고 서버에서 검증되는가? (예/아니오)
- "이전 지시를 무시하라" 류 입력이 지시로 실행되지 않고 데이터로만 처리되는가? (예/아니오)

### VIII. 고정된 출력 구조 (Structured Output)
**규칙**: AI 출력은 추천 직업 정확히 3개, 키워드 정확히 3개, 각 항목별 근거와 설명의 구조로
고정한다. 스키마 검증에 실패한 응답은 재요청하거나 오류로 처리한다.
**이유**: 예측 가능한 구조여야 화면 표시, 복사, 인쇄가 안정적으로 동작한다.
**검토 기준**:
- 응답 스키마가 정의되어 서버에서 검증되는가? (예/아니오)
- 직업·키워드가 3개 미만 또는 초과인 응답이 화면에 표시되지 않는가? (예/아니오)
- 스키마 실패 시 재요청 횟수 상한과 오류 처리가 구현되어 있는가? (예/아니오)

### IX. API 키 서버 전용 (Server-Side Secrets)
**규칙**: AI API 키는 클라이언트에 노출하지 않으며, API 호출은 서버 측에서만 수행한다.
**이유**: 키 노출은 비용 도용과 서비스 악용으로 이어진다.
**검토 기준**:
- 클라이언트 번들과 네트워크 응답에 API 키가 포함되지 않는가? (예/아니오)
- 브라우저가 AI 제공자 API를 직접 호출하지 않는가? (예/아니오)
- 키가 환경 변수로 관리되고 저장소에 커밋되지 않았는가? (예/아니오)

### X. 장애 시 안내와 입력 유지 (Graceful Failure)
**규칙**: AI 호출 실패, 응답 지연, 형식 오류 시 상황을 이해할 수 있는 안내와 재시도 수단을 제공한다.
입력한 내용은 실패 시에도 유지한다.
**이유**: 상담 중 오류로 입력을 다시 해야 하면 상담 흐름이 끊긴다.
**검토 기준**:
- 실패 유형별(호출 실패, 지연, 형식 오류) 이해 가능한 안내가 표시되는가? (예/아니오)
- 재시도 버튼이 있으며 재시도 시 입력을 다시 하지 않아도 되는가? (예/아니오)
- 지연 시 진행 중임을 나타내는 상태와 타임아웃 처리가 있는가? (예/아니오)

### XI. 명세 범위 준수 (Scope Discipline)
**규칙**: 명세에 없는 기능을 임의로 추가하지 않는다.
**이유**: 1인 개발 MVP에서 범위 확장은 일정, 품질, 개인정보 위험을 키운다.
**검토 기준**:
- 구현된 모든 기능이 명세의 요구사항에 대응되는가? (예/아니오)
- 명세에 없는 화면, 저장, 계정 기능이 없는가? (예/아니오)
- 범위 추가가 필요했다면 명세를 먼저 수정했는가? (예/아니오)

### XII. 쉬운 언어와 존중하는 표현 (Plain and Respectful Language)
**규칙**: 결과 문장은 구직자가 함께 보아도 이해할 수 있는 쉬운 언어로 작성하고, 낙인이나 위축을
주는 표현을 피한다.
**이유**: 결과를 구직자와 함께 확인하므로 표현이 상담 관계와 구직자의 자신감에 영향을 준다.
**검토 기준**:
- 프롬프트에 쉬운 언어와 낙인 금지 지침이 있는가? (예/아니오)
- 샘플 결과에 전문 용어에 대한 설명 없는 사용이나 위축시키는 표현이 없는가? (예/아니오)
- 상담사 또는 검토자가 샘플 결과를 읽고 "구직자와 함께 봐도 괜찮다"고 확인했는가? (예/아니오)

### XIII. 접근성 (Accessibility)
**규칙**: 주요 행동은 키보드만으로 수행할 수 있어야 한다. 상태는 색상만으로 구분하지 않고 텍스트를
함께 사용한다. 모든 애니메이션은 prefers-reduced-motion 사용자를 고려한다.
**이유**: 다양한 사용자와 환경에서 상담이 가능해야 한다.
**검토 기준**:
- 입력, 제출, 재시도, 복사, 인쇄를 키보드만으로 완료할 수 있고 포커스가 보이는가? (예/아니오)
- 오류·성공·로딩 상태가 색상 외에 텍스트로도 표시되는가? (예/아니오)
- prefers-reduced-motion 설정 시 애니메이션이 중지되거나 최소화되는가? (예/아니오)

### XIV. 반응형 핵심 시나리오 (Responsive Core Flow)
**규칙**: 데스크톱, 태블릿, 모바일에서 핵심 시나리오(정보 입력 → 결과 확인 → 결과 복사 또는 인쇄)가
완료되어야 한다.
**이유**: 상담 현장에서 사용하는 기기가 다양하다.
**검토 기준**:
- 세 가지 화면 크기에서 핵심 시나리오를 끝까지 수행할 수 있는가? (예/아니오)
- 가로 스크롤이나 잘림으로 인해 내용을 읽을 수 없는 화면이 없는가? (예/아니오)
- 인쇄 시 결과와 참고용 안내가 한 번에 읽기 좋게 출력되는가? (예/아니오)

### XV. 단순한 MVP와 추적 가능한 완료 (Simplicity and Traceability)
**규칙**: 단순한 MVP 구조를 우선하며, 1인 개발자가 유지보수할 수 있는 무료·저비용 기술 스택을
사용한다. 모든 구현 Task는 요구사항과 근거를 추적할 수 있어야 하며, 테스트와 빌드가 실패한 작업은
완료 처리하지 않는다.
**이유**: 유지보수 가능성과 검증 가능성이 1인 개발 프로젝트의 지속성을 결정한다.
**검토 기준**:
- 각 Task가 요구사항(또는 원칙)과 연결되어 있는가? (예/아니오)
- 완료 처리된 모든 Task에서 테스트와 빌드가 통과했는가? (예/아니오)
- 도입한 모든 도구·서비스가 무료 또는 저비용 범위이며 필요성이 설명되어 있는가? (예/아니오)

## 원칙 충돌 시 우선순위

원칙끼리 충돌하면 다음 순서로 판단한다(높은 순위가 우선).

1. **개인정보 보호·차별 방지**: 원칙 V, VI (관련: VII, IX)
2. **근거 기반 정확성**: 원칙 II, III, IV, VIII (관련: I, XII)
3. **접근성**: 원칙 XIII, XIV
4. **기능 편의성**: 원칙 X, XI, XV 중 편의 목적의 판단

충돌을 해소한 결정은 해당 명세 또는 plan 문서에 이유와 함께 기록해야 한다(MUST).

## 개발 제약

- AI 호출은 서버 측에서만 수행하며 API 키는 환경 변수로 관리한다.
- 입력 데이터와 결과는 상담사가 저장을 명시적으로 실행할 때만 저장한다(원칙 VI). 로그에는 입력
  본문을 남기지 않는다.
- 기술 스택은 인증과 저장소를 포함해 무료·저비용 도구로 한정하며 새 의존성은 필요성을 기록한다.

## 개발 워크플로 및 품질 게이트

- 모든 Task는 요구사항 또는 원칙 번호를 참조한다.
- 테스트와 빌드가 통과하지 않은 Task는 완료로 표시하지 않는다.
- 구현 후 각 원칙의 검토 기준을 예/아니오로 확인하고, "아니오"가 있으면 수정 또는 예외 기록 없이
  병합·배포하지 않는다.

## Governance

- 이 Constitution은 다른 개발 관행보다 우선한다.
- 개정은 변경 내용, 이유, 영향받는 명세·계획·Task 문서를 기록한 뒤 반영한다.
- 버전은 시맨틱 버저닝을 따른다. MAJOR: 원칙 삭제 또는 재정의, MINOR: 원칙·섹션 추가 또는
  실질적 확장, PATCH: 문구 명확화.
- 모든 plan, tasks, 구현 검토에서 원칙 준수 여부를 확인해야 하며, 위반은 정당한 이유와 함께
  기록해야 한다(MUST).
